One of the clearest remaining differences between desktop FILIUS and Filius on iPad is also one of the easiest to underestimate. The desktop application includes a Software Wizard for creating custom client and server applications. The iPad app does not offer a fully compatible version of that workflow.

This is not an overlooked editor screen. The Java feature depends on an entire execution environment, and our current iPad substitute deliberately covers only a bounded part of the same learning space. We want to explain that boundary openly: what the desktop version does, why we stopped short of copying it, what already exists on iPad, and what evidence we need before taking the next step.

## What the desktop wizard actually does

The desktop workflow goes far beyond storing a few protocol settings. It generates Java source files from client or server templates, opens those files for editing, invokes a Java compiler, and registers the compiled application so it can be installed on a simulated computer.

Those templates are connected to FILIUS’s own Java application classes, simulated sockets, background threads, and Swing windows. A learner can change message processing, add program logic, and alter the interface. The result is executable Java that runs inside the same desktop environment as FILIUS.

That last point matters. A source editor alone would reproduce the appearance of the feature, but not its result. Full compatibility would require the edited program to compile, load, interact with the simulator, display its interface, stop cleanly, and have clearly defined behavior when projects move between systems.

## Why this is not a direct port

Filius on iPad is a native Swift and SwiftUI application. It does not contain a Java compiler, a Java Virtual Machine, a Swing compatibility layer, or a system for loading newly compiled Java classes at runtime.

Adding those pieces solely for this feature would create a second application platform inside the iPad app. We would then have to maintain compatibility with the Java wizard’s internal APIs, threading model, user-interface assumptions, storage, lifecycle, error reporting, and simulator integration. Even source generated by the standard templates is coupled to desktop FILIUS classes; it is not portable code that can simply be handed to the native iPad runtime.

Executing user-edited code would also expand the failure and trust boundary considerably. A classroom tool needs predictable project files, bounded resource use, clear cleanup, and deterministic simulated networking. A general code runtime makes each of those properties harder to explain, test, and support.

For those reasons, we decided not to pursue arbitrary Java, JVM, or Swing execution as the route to parity.

## We chose the learning outcome over the mechanism

Our parity question is not “Can we reproduce every desktop dialog?” It is “Can a learner perform the experiment, observe the network behavior, and explain the result?”

That led to a native, declarative protocol-application builder. Instead of writing source code, a user defines a client or server, chooses TCP or UDP and a port, then provides bounded client messages or ordered request-and-response rules. The application runs only through the simulated network engine. It cannot open a connection to the iPad’s real network, load a script, or introduce a new native window.

This smaller model gives us useful properties:

- behavior is deterministic and can be validated before it runs;
- traffic appears in the same simulated packet evidence as built-in applications;
- custom definitions can be installed on virtual PCs and notebooks;
- stopping, uninstalling, resetting, and deleting devices can clean up sockets predictably;
- native saves and recovery retain the definitions without inventing Java classes.

That is meaningful functionality, but it is a **substitution**, not a compatible implementation of the Java Software Wizard.

## Why the iPad builder remains experimental

The current builder can model exact text-message exchanges. It cannot express arbitrary calculations, loops, state machines, custom Java interfaces, or general library use. It also does not import and execute an existing Java source project.

Its project format is native to Filius on iPad. When a project is exported to the Java `.fls` format, native protocol definitions are omitted with a compatibility warning rather than being disguised as Java applications. Conversely, preserving unknown desktop content while opening and resaving a project does not make that content executable on iPad.

There is also a product question we have not answered well enough: **Which real lessons require learners to construct a custom application, and what is the smallest tool that serves those lessons clearly?**

Without representative classroom tasks, adding more controls would be guesswork. The present exact-message workflow is useful for technical evaluation, but it is not yet intuitive enough to put in front of every learner. It therefore stays off by default behind **Settings → Experimental features → Enable protocol applications**.

## How we may move forward

The next step should not be “add more programming features.” It should be a short discovery phase led by teaching needs.

Before redesigning the builder, we want representative lessons from teachers or curriculum owners. Each lesson should identify the learning objective, the minimum custom protocol behavior, the expected classroom workflow, and how the result should be shared or assessed.

If that need is confirmed, a guided **Protocol Lab** is the most promising direction. We would investigate:

1. a small set of teachable client/server templates;
2. a visual request-and-response timeline instead of a form full of implementation details;
3. a live preview of the packets an action would create;
4. validation messages written in networking terms rather than compiler terminology;
5. a documented, bounded format for sharing native protocol definitions;
6. translation of a limited set of common patterns produced by the desktop wizard.

The last item must remain deliberately narrow. Recognizing and translating standard template patterns may be feasible. Promising to understand or execute arbitrary Java source would not be honest.

Any redesigned workflow should remain experimental until teachers can complete representative lessons without needing knowledge of the codebase, and until save, recovery, export, accessibility, and runtime cleanup have been tested as one complete classroom path.

## What to plan for today

Lessons that depend on editing and compiling custom Java applications should continue to use desktop FILIUS. On iPad, use the built-in simulated applications for production classroom work and treat the protocol builder as an evaluation feature only.

If an existing `.fls` project references a desktop-only custom application, test the complete lesson before class. A project opening successfully proves file compatibility; it does not prove that every referenced application can run.

This gap is real, but so is the reason for it. We would rather describe a deliberate, limited substitute accurately than label an incomplete runtime as full parity. The future of the feature should be shaped by the experiments learners need—not by the fact that the desktop implementation happens to use Java.
